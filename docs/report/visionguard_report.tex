\begin{abstract}
This project develops a computer vision system for gesture recognition and continuous user authentication.
The system uses a standard webcam to observe the user, recognize predefined gestures, and enable gesture-based interaction with a computer.
In addition to gesture control, the project investigates facial recognition and user presence monitoring so that the workstation can verify whether an authorized user is still present during an active session.
The prototype combines a desktop application with a local AI service and uses technologies such as Python, JavaScript, OpenCV, MediaPipe, PyTorch-based model components, and local model execution.
The goal is to improve both usability and workstation security while keeping biometric and camera data local and under user control.
\end{abstract}

\section{Introduction}
Modern desktop systems still depend mainly on keyboards, touchpads, passwords, and short authentication checks.
These inputs work well for many tasks, but they do not always match situations where the user needs fast interaction, hands-free control, or continuous confidence that the right person is operating the system.
Camera-based computer vision can help with this problem because it allows the system to observe gestures and user presence without requiring a separate physical controller.

VisionGuard explores this idea through a local desktop application.
The system connects a live camera view with gesture recording, gesture training, model monitoring, face and presence verification, and action execution.
Instead of only asking whether the user logged in once, the application is designed around an ongoing security workflow: the camera session is started, the user records gestures, the model is trained from local samples, and live inference checks whether the current movement and user presence match an authorized session.

The project focuses on a practical balance between usability and control.
The user can define gestures, choose what action each gesture should trigger, review sample thumbnails, send the gesture to training, and then monitor model state during live use.
The system does not replace traditional authentication.
Instead, it shows how local computer vision can become an additional layer for user verification and workstation control.

\subsection{Motivation}
The motivation for VisionGuard comes from two common weaknesses in desktop use.
The first weakness is interaction speed.
Many desktop actions are simple but repeated often: opening an application, changing volume, muting sound, clicking, or sending a shortcut.
These actions are not difficult, but they require the user to move attention away from the current task.
A gesture interface can reduce that cost when the action is frequent and the gesture is easy to remember.

The second weakness is session trust.
After login, most desktop systems assume that the same user remains in front of the computer.
This assumption is not always valid in study rooms, shared laboratories, offices, and demonstrations.
If the authorized user leaves the workstation, another person may still be able to interact with the active session.
Continuous authentication addresses this problem by checking the user during the session instead of only at the beginning.

VisionGuard combines these two concerns because both can use the same local camera source.
The camera can support gesture-based commands and can also provide evidence about user presence.
The challenge is to make this useful without turning the camera into an uncontrolled privacy risk.
For that reason, the project is designed around local processing, visible status information, and explicit user control.

\subsection{Problem Statement}
The main problem is to design and build a local desktop application that can recognize user-defined gestures and support continuous user authentication without relying on cloud processing.
The application must connect a user interface, a camera stream, a local AI service, a dataset workflow, and desktop action execution.
It must also provide enough feedback for the user to understand the state of the system.

The problem is not only a machine-learning problem.
It also includes software architecture, user interaction, data management, security expectations, and platform constraints.
A recognition model is useful only if the rest of the system can collect good samples, train reliably, report state clearly, and prevent accidental or unsafe actions.
Therefore, the work focuses on the complete pipeline from recording to action execution.

\subsection{Contributions}
The main contributions of the BSP are:

\begin{itemize}[leftmargin=*]
  \item A desktop prototype that connects camera monitoring, gesture recording, model training, and gesture-triggered actions.
  \item A local AI service that handles hand-presence checks, training jobs, model status, and inference requests.
  \item A shared contract layer that keeps the desktop application and Python service aligned.
  \item A workflow design for continuous authentication using face recognition and user presence monitoring.
  \item A privacy-aware architecture where camera samples and inference requests stay on the user's machine.
\end{itemize}

\section{Related Work}
\subsection{Gesture Recognition}
Gesture recognition systems try to understand hand or body movement from sensor data.
Traditional systems often used depth cameras, wearable sensors, or handcrafted image features.
More recent approaches use machine learning and landmark detection to extract richer information from normal camera input \cite{oudah2020handgesture,alfarid2022structured}.
MediaPipe Hands is an example of a widely used hand-tracking pipeline that can detect hand landmarks in real time and support interactive applications \cite{zhang2020mediapipe}.
On-device gesture-recognition work builds on this idea by combining a hand skeleton tracker with a gesture classifier for predefined static gestures \cite{sung2021gesture}.

Gesture recognition is useful in human-computer interaction because it can reduce friction in tasks where keyboard and mouse input is slow or inconvenient.
For a desktop system, gestures can act as shortcuts for repeated actions.
However, the system must also avoid accidental activations.
This is why confidence thresholds, cooldown periods, and clear event feedback are important parts of the design.

\subsection{Continuous Authentication}
Continuous authentication checks user identity or user behavior after the initial login step.
Instead of trusting a session forever, the system keeps collecting evidence that the active user still matches the expected user.
Research in this area includes keystroke dynamics, mouse behavior, face recognition, gait, touch patterns, and multimodal approaches \cite{patel2016continuous}.
Recent surveys also emphasize that continuous authentication must balance security, privacy, and usability instead of optimizing only recognition accuracy \cite{baig2021security}.

VisionGuard is related to continuous authentication because it treats camera input as an ongoing signal.
The declared BSP scope includes face detection, face recognition, and user presence monitoring.
These functions allow the system to verify whether the detected user belongs to an authorized set of users and to secure the workstation when the authorized user is no longer present.
Modern face-recognition systems commonly use learned face embeddings, where image similarity can be compared in a compact feature space \cite{schroff2015facenet,deng2019arcface}.

\subsection{Local AI and Privacy}
Camera-based systems can introduce privacy risks because video frames may contain faces, rooms, documents, or other sensitive context.
For this reason, local processing is an important design choice.
In VisionGuard, the desktop application and AI service run on the same machine.
The camera frames and sample files are handled locally, and the model service is accessed through a local URL.
This reduces reliance on remote processing and gives the user more direct control over the data flow.
This design direction is consistent with privacy-focused discussions in continuous authentication and face recognition, where biometric collection, storage, and inference can all introduce risk \cite{baig2021security,sun2025privacy}.

\section{Background}
\subsection{Why Gesture Control Needs Reliability}
Gesture control is useful only when it is predictable.
A gesture that fails too often becomes frustrating, while a gesture that triggers too easily becomes unsafe.
This is especially important when gestures are connected to desktop actions such as keyboard shortcuts or mouse clicks.
The system therefore needs a clear training workflow, a visible model state, and a confidence threshold before execution.

\subsection{Why Authentication Needs More Context}
Passwords and login screens usually check identity at one point in time.
After that, the computer often assumes that the same person remains in control.
In shared rooms, labs, or workstations, this assumption can be weak.
Continuous authentication adds context by checking signals during the session.
VisionGuard uses the camera as the first input channel for this kind of context.

\subsection{Project Constraints}
The project was built as a local desktop prototype.
The declared BSP target is a multi-platform application for Windows, Linux, and macOS.
The current prototype demonstrates the full gesture workflow locally, while the implemented desktop action bridge currently targets macOS because it uses platform commands such as \texttt{open} and \texttt{osascript}.
The AI service is implemented as a Python service running on \texttt{127.0.0.1:8765}.
The interface can render in a browser for development, but gesture actions, file persistence, and inference integration are intended for the Electron desktop environment.
Docker containers are used to make the service environment more reproducible and to reduce differences between local development machines.
This is useful because computer-vision dependencies can be sensitive to Python versions, native libraries, and operating-system packages.

\section{Project Objectives}
This project creates a local computer-vision application for secure and efficient desktop interaction.
The main goals of the project are:

\begin{itemize}[leftmargin=*]
  \item Build a desktop interface where the user can start a camera session and monitor camera state.
  \item Allow users to record gesture samples and map each gesture to a desktop action.
  \item Store gesture samples locally and send structured sample references to an AI service.
  \item Train a gesture-recognition model from captured samples.
  \item Implement face detection and face recognition mechanisms for continuous user verification.
  \item Monitor user presence and support workstation security when the authorized user is no longer present.
  \item Run live inference against camera frames and show prediction confidence.
  \item Execute desktop actions only when the prediction confidence is high enough.
  \item Support a multi-platform design that can operate on Windows, Linux, and macOS.
  \item Evaluate recognition accuracy, authentication performance, task execution time, latency, compatibility, and reliability.
\end{itemize}

The system is designed to support the user, not to hide decisions from them.
The interface shows model health, training status, camera state, prediction output, and recent events so the user can understand what the system is doing.

\subsection{Functional Requirements}
The functional requirements define what the prototype must be able to do during normal use.
The application must be able to start and stop a camera session from the desktop interface.
It must show whether the camera is active, whether frames are being received, and whether the AI service is reachable.
The user must be able to create a gesture profile, select the action connected to that gesture, and record enough samples for training.

The system must reject unusable samples when no hand is detected.
This requirement is important because weak samples reduce recognition quality and make later evaluation less meaningful.
After a gesture has enough accepted samples, the user must be able to save it and send it to the AI service.
The AI service must then create a training job, report progress, and expose the current model state to the desktop application.

During live use, the application must periodically send camera frames to the AI service for inference.
If a trained gesture is detected with a confidence above the configured threshold, the desktop layer must execute the mapped action.
The application must also record the event in the interface so the user can see what happened.
For the authentication part, the system must provide a path for face detection, face recognition, and user presence monitoring.

\subsection{Non-Functional Requirements}
The non-functional requirements are equally important because the project works with camera data and desktop actions.
The first requirement is local processing.
Camera frames, samples, model files, and biometric information should remain on the same computer whenever possible.
The second requirement is responsiveness.
The user interface should stay usable while the AI service validates samples, trains models, or runs inference.
Another requirement is reproducibility.
The AI service should run in a predictable environment so that Python, OpenCV, MediaPipe, and model dependencies behave the same way across development setups.
Containers help with this requirement by isolating service dependencies from the host machine.

Reliability is another requirement.
The application should not execute actions when the camera is inactive, the model is not ready, or the prediction confidence is too low.
It should also avoid repeated activation from one continuous gesture.
This is handled through confidence thresholds, model readiness checks, and cooldown logic.

The final non-functional requirement is portability.
The BSP declaration states that the target platform is Windows, Linux, and macOS.
The current implementation demonstrates the complete flow on macOS, but the architecture must leave space for platform-specific action adapters.
This means the core recognition and authentication logic should not depend on one operating system.

\subsection{Use Cases}
VisionGuard supports several practical use cases.
In a study environment, a student can use simple gestures as shortcuts while reading, presenting, or testing software.
In a laboratory setting, the system can help when the user's hands are busy or when touching the keyboard is inconvenient.
In a shared workspace, presence monitoring can warn the application when the authorized user is no longer visible.

The project is also useful as an experimental platform.
Different gesture classes, confidence thresholds, training sample counts, and model families can be tested without rewriting the desktop application.
Because the AI service is separated from the interface, future work can replace the recognition model while keeping the same user workflow.

\section{Methods}
This section explains how VisionGuard was built.
The system combines desktop development, local web technologies, and Python computer-vision processing.

\subsection{System Design Approach}
The system follows a modular design.
Each part has a clear responsibility and communicates through typed contracts.
The three main ideas are:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Local processing:} Camera frames, gesture samples, training jobs, and inference requests stay on the local machine.
  \item \textbf{Typed integration:} The desktop app and AI service use a shared contract for datasets, training jobs, model status, and inference results.
  \item \textbf{User-centered control:} The user records gestures, reviews captured samples, starts training, and sees model and event feedback.
\end{enumerate}

\subsection{Methodology}
The project follows an iterative development process with five phases:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Requirements analysis and system design:} Define the gesture-control and continuous-authentication goals, platform requirements, and local-processing constraints.
  \item \textbf{Gesture recognition development:} Capture webcam frames, validate hand presence, record gesture samples, train recognition models, and connect predictions to actions.
  \item \textbf{Face detection and authentication development:} Detect the visible user, compare the detected face with authorized profiles, and monitor whether the user remains present.
  \item \textbf{Multi-platform integration and testing:} Structure the desktop layer so Windows, Linux, and macOS can be supported through platform-specific adapters.
  \item \textbf{Evaluation, documentation, and presentation:} Measure accuracy, authentication performance, execution time, latency, compatibility, and reliability, then document the resulting prototype.
\end{enumerate}

\subsection{Technical Setup}
VisionGuard has three main technical parts and follows the technical stack declared for the BSP:

\begin{itemize}[leftmargin=*]
  \item \textbf{Programming languages:} Python and JavaScript are used for the AI service and desktop application.
  \item \textbf{Computer vision:} OpenCV supports image processing, face detection, and camera-frame analysis.
  \item \textbf{Gesture tracking:} MediaPipe supports hand tracking and hand-presence checks.
  \item \textbf{Machine learning:} PyTorch-based model components are part of the planned recognition and authentication pipeline \cite{paszke2019pytorch}.
  \item \textbf{Desktop application:} Electron, React, TypeScript, and Vite are used to build the user interface and desktop bridge.
  \item \textbf{Shared kernel:} A TypeScript package defines the AI model service contract used by the desktop layer.
  \item \textbf{AI service:} Python and FastAPI support dataset creation, training jobs, model status, hand-presence checks, and inference.
  \item \textbf{Containers:} Docker is used to run service components in a controlled environment and to make dependency setup more repeatable.
  \item \textbf{Development and version control:} Visual Studio Code is used as the development environment, with Git and GitHub used for version control.
  \item \textbf{Operating systems:} The declared target is cross-platform support for Windows, Linux, and macOS.
\end{itemize}

\section{System Framework}
\subsection{Framework Overview}
The VisionGuard workflow has five main stages.
First, the user starts a camera session.
Second, the user records gesture samples and saves them as a gesture definition.
Third, the saved gesture is sent to the AI service for training.
Fourth, the system verifies user presence and supports continuous authentication using face detection and recognition.
Fifth, live inference uses the trained model to detect gestures and trigger desktop actions.

\subsection{Stage 1: Camera Session}
The camera session is the starting point of the system.
The user selects a camera and presses \textit{Start Session}.
When the camera is active, the interface shows the live preview, camera resolution, frame rate, and readiness state.
If the camera is inactive, the monitor shows a standby illustration and explains that the user must start a session.

The camera workflow is intentionally explicit.
The user decides when the session begins, and the interface makes the camera state visible.
This is important for trust because the application uses visual input.
The user should not need to guess whether the camera is running or whether frames are being processed.
The monitor therefore separates camera state, model state, identity state, and recent events into visible areas.

From an implementation perspective, the renderer owns the live preview and frame capture loop.
Frames are converted into image data only when the system needs a sample or an inference request.
This reduces unnecessary processing and keeps the interface responsive.
The Electron layer then acts as the bridge between the browser-based renderer and local desktop resources.

\subsection{Stage 2: Gesture Recording}
The gesture panel allows the user to create a new gesture.
The user chooses an action type, enters a gesture name, enters an action target, and records samples.
The application expects 12 valid samples before the gesture can be saved.
During capture, the system checks whether a hand is present in the frame.
This prevents empty or unusable samples from entering the training dataset.

Each accepted sample becomes part of a local gesture dataset.
The user can review the captured thumbnails before saving the gesture.
This step is useful because it gives immediate feedback about sample quality.
If the samples are blurred, poorly framed, or inconsistent, the user can record the gesture again before training.

The sample count is kept small enough for a lightweight prototype but large enough to capture basic variation.
A user may perform the same gesture at slightly different distances, angles, and hand positions.
The training set therefore needs more than one image, even for a static gesture.
At the same time, requiring too many samples would make the application slow to use.
The current requirement of 12 valid samples is a practical compromise for development and demonstration.

\subsection{Stage 3: Training}
When a gesture is ready, the user can send it to training.
Electron sends the gesture labels and sample references to the AI service.
The AI service creates a dataset, starts a training job, updates progress, and saves a model artifact in the local model directory.
The desktop app polls the training job and updates the gesture status when the job is completed, failed, or cancelled.

Training is treated as a job instead of a blocking request.
This matters because model training can take longer than a normal interface action.
If the desktop app waited for the request to finish directly, the user could be left with an unresponsive screen.
With a job-based design, the service can report progress while the interface remains active.

The model artifact is stored locally after training.
The desktop application does not need to know the internal format of the model.
It only needs to know whether a ready model exists, which gestures it supports, and whether inference can be started.
This keeps the user interface independent from the training implementation.

\subsection{Stage 4: Face Recognition and User Presence}
The continuous-authentication part of the BSP focuses on verifying whether the detected user belongs to an authorized set of users.
The planned workflow uses face detection to locate the user, face recognition to compare the detected face with authorized profiles, and presence monitoring to check whether the authorized user remains at the workstation.
If the authorized user is no longer present, the system can secure the workstation or block sensitive actions.
Deep face-recognition surveys show that this type of verification is commonly built from detection, alignment, feature extraction, and embedding comparison \cite{wang2018deepface,wang2022surveyface}.

The presence signal is different from the gesture signal.
Gesture recognition asks what command the user is performing.
Presence monitoring asks whether the correct user is still at the workstation.
For that reason, the authentication pipeline should run with separate thresholds and separate state.
A gesture can be rejected because it is unclear, while a user can still be considered present.
Likewise, a clear gesture should not trigger a sensitive action if the authorized user is not verified.

The intended authentication workflow begins with an enrollment step.
The authorized user records several face samples under normal lighting conditions.
The system extracts a representation from these samples and stores it locally.
During an active session, the system compares the current face representation with the enrolled profile.
If no face is detected for a defined period, or if the detected face does not match the authorized profile, the application can mark the session as unverified.

\subsection{Stage 5: Live Inference and Action Execution}
Live inference runs only when the camera is active, at least one gesture is trained, the AI service is online, and the model status is ready.
The renderer captures frames periodically and sends them through Electron to the AI service.
The AI service returns predictions with confidence values.
If the best prediction matches a trained gesture and the confidence is high enough, the desktop layer executes the mapped action.
The current action confidence threshold is 0.92, and a cooldown period prevents one gesture from repeatedly triggering the same command.

The threshold is intentionally high because desktop actions have side effects.
A false positive is more serious than a missed gesture when the action changes application state.
For example, an accidental shortcut or click can interrupt work.
The cooldown period also improves safety by preventing a single held gesture from being interpreted as many separate commands.

The event timeline is part of the control loop.
It shows when a prediction was received, whether the confidence was sufficient, and which action was triggered.
This makes the system easier to debug and easier to demonstrate.
Without this feedback, the user would only see the final desktop action and would not know whether the recognition model, threshold, or action bridge caused a problem.

\section{System Building}
\subsection{Technology Stack and Architecture}
The desktop app is built with a modern TypeScript stack.
React is used for the renderer interface, Electron provides access to desktop capabilities, and Vite supports development and build tooling.
The AI service is implemented with FastAPI.
Computer-vision work uses OpenCV and MediaPipe for hand-related processing, with PyTorch-based models planned for stronger recognition and authentication tasks \cite{bradski2000opencv,zhang2020mediapipe,paszke2019pytorch}.
The project is organized as a workspace with separate packages for the desktop app, shared contracts, and AI service.

The workspace structure separates concerns.
The renderer code focuses on interface state, camera preview, user input, and feedback.
The Electron main process handles local file access and operating-system actions.
The shared package defines the data contract between TypeScript and Python.
The Python service handles computer-vision processing and model operations.

This separation makes the project easier to test and extend.
For example, the desktop interface can be improved without changing the model code.
The AI service can also be replaced with a stronger implementation if it preserves the same service contract.
This is useful for a BSP because the prototype can show a complete system while leaving room for deeper research work in later iterations.

\subsection{Custom Building Components}
\subsubsection{Live Monitor}
The live monitor is the main operating screen.
It shows the camera preview, model health, event timeline, active-user panel, and gesture activity.
This screen is designed for repeated use because the user needs to quickly understand whether the system is ready, offline, training, or waiting for a gesture.

The monitor is organized around status first and controls second.
This is deliberate.
When a camera-based system is running, the user needs to know the current state before deciding what to do next.
For example, if the AI service is offline, pressing gesture controls should not appear to work.
If the model is still training, the interface should not suggest that live inference is ready.
The monitor therefore gives priority to camera state, model readiness, identity state, and recent events.

The event timeline also supports debugging.
During development, many problems can look similar from the outside.
A gesture might fail because the camera is not active, because the hand was not detected, because the model is missing, because confidence is too low, or because the action adapter failed.
By showing recent events, the application gives a short explanation of the last system decisions.
This makes the prototype easier to demonstrate and easier to improve.

\subsubsection{Gesture Library}
The gesture library stores gesture definitions with names, action types, targets, confidence goals, sample counts, and training state.
The current application supports actions for opening an application, reducing volume, increasing volume, muting audio, sending a keyboard shortcut, and clicking the mouse.

The gesture library is designed as a small training workspace.
The user does not only select a gesture from a fixed list.
Instead, the user creates a gesture, records examples, connects it to an action, and sends the result to the local AI service.
This is important because the project is about user-defined interaction.
Different users may prefer different gestures for the same action.

The interface must also protect the user from incomplete gestures.
A gesture with too few samples should not be treated as ready for training.
A gesture that has not been trained should not be treated as ready for live inference.
These states are visible in the library so the user can understand the progress from recording to training to use.

\subsubsection{AI Service Contract}
The shared contract defines the data shapes used across the desktop app and AI service.
Important objects include \texttt{TrainingDataset}, \texttt{TrainingJob}, \texttt{ModelStatus}, \texttt{InferenceResult}, and \texttt{HandPresenceResult}.
This keeps the desktop and Python service aligned even though they are implemented in different languages.

The contract is one of the most important engineering choices in the project.
Without a shared definition, the renderer, Electron main process, and Python service could easily disagree about field names, status values, or error formats.
That would make failures harder to find because each layer would interpret the same request differently.
The shared model also gives the user interface a stable way to display model state and training progress.

\subsubsection{Local Storage}
Gesture samples are stored as local files instead of being sent to a remote database.
The desktop layer keeps references to these files and sends structured paths or identifiers to the AI service.
This approach supports the privacy goal of the project and also makes debugging easier.
During development, the saved samples can be inspected directly to check whether the camera capture and hand-presence validation are working correctly.

Local storage also creates responsibilities.
The application should avoid uncontrolled growth of sample folders, should handle missing files gracefully, and should make it clear which samples belong to which gesture.
For a production version, metadata about gestures, samples, model versions, and training results should be persisted in a small local database.
The current prototype focuses on the end-to-end workflow and leaves full dataset management as future work.

\subsubsection{Hand-Presence Detection}
Before a sample is accepted, the system checks whether a hand is visible.
The Python worker uses MediaPipe hand detection and additional image-processing methods to locate likely hand regions.
This makes the training set cleaner because the application avoids saving frames where the user has not shown a hand.

\subsubsection{Face Verification and Presence Monitoring}
The BSP declaration includes face detection, face recognition, and user presence monitoring as part of the authentication goal.
This module is responsible for detecting the visible user, comparing the detected face with authorized users, and deciding whether the workstation should remain active.
The implementation can use OpenCV for detection and PyTorch-based models for recognition and verification.
FaceNet and ArcFace are especially relevant because both focus on learning discriminative face embeddings for verification and recognition \cite{schroff2015facenet,deng2019arcface}.

\subsubsection{Ethical and Privacy Controls}
Because the project processes visual information from a camera, the system must treat privacy as a central design constraint.
Facial data is used only for local user verification, biometric information is not shared with third parties, data storage is minimized where possible, and user consent is required before collecting or processing facial information.
These constraints follow from the privacy and usability risks identified in continuous-authentication and privacy-preserving face-recognition literature \cite{baig2021security,sun2025privacy}.

\subsubsection{Desktop Actions}
The Electron main process executes desktop actions after a confident match.
On macOS, the implementation uses system commands to open apps, adjust volume, toggle mute, send keyboard shortcuts, or issue a mouse click.
The BSP target is to support Windows, Linux, and macOS through separate platform adapters.
The current prototype demonstrates the action bridge on macOS; other operating systems require equivalent adapters before the application can be considered fully cross-platform.

\subsection{Service Interface}
The AI service exposes a small set of local endpoints.
The desktop application uses these endpoints to check health, validate frames, create datasets, start training, inspect model state, and request inference.
The service is local, so the network boundary is mainly an architectural boundary rather than a cloud dependency.

\subsection{Containerized Service Environment}
Docker is used to run project components in containers during development and testing.
The main reason is dependency control.
The AI service depends on Python packages and native computer-vision libraries.
These dependencies can behave differently across operating systems or even across machines with different Python installations.
A container gives the service a more predictable execution environment.

Containerization also makes onboarding easier.
Instead of installing every dependency directly on the host machine, the developer can run the service in an isolated environment that contains the required packages.
This reduces setup errors and makes it easier to reproduce the same behavior during demonstrations.
For a BSP project, this matters because the final result should not depend only on one manually configured laptop.

Docker also helps separate the desktop application from the AI service.
The Electron application can treat the service as a local process available through \texttt{127.0.0.1:8765}, while the service itself can run with its own Python environment.
This separation is close to the final architecture of the system.
The desktop layer sends structured requests, and the containerized AI service returns structured results.

There are still practical limits.
Camera access from containers can require extra configuration, especially on macOS and Windows.
For that reason, the desktop camera preview remains part of the Electron application, while the service focuses on processing frames and returning model results.
This design keeps camera permissions in the desktop layer and keeps model dependencies in the service layer.

\subsection{Error Handling}
The prototype must handle errors at several levels.
The camera can be unavailable, the AI service can be offline, training can fail, a sample can be rejected, or the desktop action can be unsupported on the current platform.
The interface should report these states instead of hiding them.
Clear reporting is especially important in a system that combines user interaction and AI predictions.

VisionGuard uses visible model and event states to make errors understandable.
For example, if inference is not running because no model is ready, the monitor can show that the problem is model state rather than camera state.
If a desktop action fails because the operating system adapter is missing, the event log can show that recognition worked but action execution did not.
This separation helps both the developer and the user.

\subsection{Interface Design}
The interface is built for a user who needs to operate the system repeatedly, not only read an explanation of it.
For that reason, the first screen is the working monitor rather than a landing page.
The user can start the camera, inspect model state, check identity status, and follow the event timeline without moving through several pages.

The design uses separate panels for the main tasks.
The live monitor focuses on the current session.
The gesture view focuses on recording and training.
The model and settings views focus on configuration, identity context, and system status.
This separation keeps the main workflow readable.
It also makes the interface easier to extend because new authentication settings or model details can be added without overcrowding the gesture recorder.

The screenshots in Figures \ref{fig:monitor}, \ref{fig:gestures}, and \ref{fig:models} show this structure.
The monitor screenshot belongs near the framework overview because it shows the running system.
The gesture screenshot belongs near the recording stage because it shows sample capture and action mapping.
The model screenshot belongs near the expected outcome because it shows that model state and identity context are separated from the main interaction flow.
Placing the figures close to the related text makes the report easier to read.

\subsection{Data Flow During Normal Use}
During a normal session, the data flow begins when the user starts the camera.
The renderer receives video frames and displays the live preview.
When the user records a gesture sample, the current frame is sent through the desktop bridge for validation and storage.
The AI service checks whether a hand is visible.
If the sample is accepted, the application stores it locally and updates the gesture sample count.

When the user starts training, the desktop layer sends the gesture label and saved sample references to the AI service.
The service creates a dataset description and starts a training job.
The desktop app does not block while training is running.
Instead, it polls the job state and updates the interface.
After training, the model state becomes ready and live inference can begin.

During live inference, the renderer sends frames at intervals rather than sending every camera frame.
This keeps processing cost under control.
The AI service returns the most likely gesture label and a confidence value.
The desktop layer checks whether the result is allowed to trigger an action.
The checks include model readiness, gesture match, confidence threshold, cooldown time, and user verification state.
Only then does the application execute the desktop action.

\subsection{Security Boundaries}
VisionGuard has several security boundaries.
The first boundary is between the renderer and the operating system.
The renderer should not directly execute system commands.
It sends structured requests to the Electron main process, which is responsible for deciding which actions are allowed.
This reduces the risk of uncontrolled command execution from the user interface.

The second boundary is between the desktop application and the AI service.
The service receives frames and sample references, but it does not control the desktop.
It returns recognition results.
The desktop layer decides whether a result is safe to use.
This separation is important because an AI prediction should not automatically become an operating-system command.

The third boundary is the local machine itself.
The project avoids remote camera processing.
That choice does not remove all privacy concerns, but it gives the user and developer more direct control over storage and inference.
It also makes the system easier to explain in the BSP report because the camera data path is limited to the local application.

\section{Results}
\subsection{Functional Results}
The project reached the following main results:

\begin{itemize}[leftmargin=*]
  \item A working Electron desktop interface for camera monitoring and gesture management.
  \item A gesture recorder that captures samples and checks hand presence before saving.
  \item A local AI service with endpoints for datasets, training jobs, model status, hand detection, and inference.
  \item A shared contract layer between the desktop app and AI service.
  \item A live inference workflow that connects predictions with action execution.
  \item A dashboard that reports model health, inference state, and recent events.
  \item A project architecture that can be extended with face recognition, presence monitoring, and cross-platform action adapters.
\end{itemize}

\subsection{Evaluation Criteria}
The BSP declaration defines the evaluation around recognition accuracy, authentication performance, execution time of individual processing tasks, overall latency, compatibility across supported operating systems, and system reliability.
For gesture recognition, this means measuring how often predefined gestures are correctly detected and how often incorrect gestures trigger actions.
For continuous authentication, this means measuring whether authorized users are correctly accepted, unauthorized users are rejected, and absence from the workstation is detected quickly enough.
For system performance, this means measuring camera-frame processing time, model inference time, desktop action execution time, and end-to-end latency.

\subsection{Evaluation Method}
The evaluation should use repeated trials instead of one demonstration run.
For gesture recognition, each predefined gesture should be performed several times under similar conditions.
The test should include correct gestures, non-target hand movements, and empty frames.
This makes it possible to measure true positives, false positives, false negatives, and rejected frames.

For continuous authentication, the evaluation should include at least three cases.
The first case is the authorized user sitting in front of the workstation.
The second case is no user present.
The third case is a different user sitting in front of the workstation.
These cases are enough to test the basic acceptance, rejection, and absence behavior.
More users and lighting conditions would improve the evaluation, but the basic cases already show whether the pipeline works.

The performance evaluation should record timing at each stage.
The most important values are frame capture time, hand or face processing time, model inference time, action execution time, and total time from frame capture to visible result.
These measurements show whether the prototype is only accurate or also practical for interaction.
Gesture control must feel immediate; otherwise, the user will return to keyboard and mouse input.

\subsection{Testing Procedure}
A practical test session can be organized in four steps.
First, the user records the gesture samples and trains the model.
Second, the user performs each trained gesture in a fixed order while the application records predictions and actions.
Third, the user performs random movements and no-gesture frames to test accidental activation.
Fourth, the user tests presence and face-recognition states by leaving the workstation and by replacing the authorized user with another person.

The test should be repeated under at least two lighting conditions.
Camera-based systems are sensitive to shadows, reflections, and poor lighting.
A model that works only under perfect light is not reliable enough for normal desktop use.
The evaluation should therefore report both the best-case and more difficult conditions.

Results should be presented as counts and percentages.
For example, the report can state how many times each gesture was correctly detected out of the total number of trials.
It can also report the number of accidental activations during non-target movements.
This style of reporting is simple, but it is clear and useful for a BSP prototype.

\subsection{Security and Privacy Relevance}
VisionGuard is relevant because it keeps sensitive camera processing local.
The system does not require a cloud service to train or run gesture inference.
This is important because camera frames may contain personal information.
The project also shows that authentication-related features should be visible and explainable.
The user can see whether the system is online, whether a model is trained, whether inference is ready, and what action was triggered.

\section{Discussion}
\subsection{Practical Benefits}
The main practical benefit of VisionGuard is the integration of several ideas into one desktop workflow.
Gesture recognition alone is useful, but it becomes more practical when the user can record gestures, save them, train a model, and immediately test live inference in the same application.
Continuous authentication alone is also useful, but it becomes easier to understand when the interface shows identity state and presence state as part of normal monitoring.

The local architecture is another benefit.
Many computer-vision systems depend on remote services for storage or inference.
That approach can be powerful, but it is not ideal for biometric and camera data.
VisionGuard shows that a useful prototype can be built with a local service and local files.
This makes the data flow easier to explain and easier to control.

\subsection{Design Trade-Offs}
The project makes several trade-offs.
The first trade-off is between simplicity and model strength.
A lightweight model and a small sample count make the prototype easier to run and demonstrate.
However, stronger recognition may require larger datasets, temporal features, and more training time.
The current design supports this future work because the AI service can be improved without replacing the desktop interface.

The second trade-off is between automation and user control.
It would be possible to hide more details from the user, but this would make the system harder to trust.
VisionGuard instead shows camera state, model state, event history, and training progress.
This adds some interface complexity, but it gives the user a clearer view of what the system is doing.

The third trade-off is platform support.
The BSP target includes Windows, Linux, and macOS.
The current action implementation demonstrates the concept on macOS, where system commands can open applications and control some desktop behavior.
Full cross-platform support requires separate adapters because each operating system exposes different mechanisms for shortcuts, audio control, window control, and security permissions.

\subsection{Limitations}
The current prototype has limitations.
The gesture dataset is small, so recognition quality depends strongly on how consistently the user records samples.
The system also depends on webcam quality, lighting, background, and hand visibility.
If the hand is partially outside the frame or the room is dark, hand detection can fail.

The continuous-authentication part is also not complete as a production security system.
The report describes the intended face-recognition and presence-monitoring workflow, and the architecture leaves space for it, but a deployed authentication system would need stronger testing, anti-spoofing controls, secure storage of biometric templates, and clear consent handling.
It would also need careful review before being used for high-risk access control.

Another limitation is persistence.
The prototype stores important artifacts locally, but a more mature version should store gesture metadata, model versions, evaluation results, and audit information in a structured way.
This would make it easier to compare experiments and reproduce results.

\subsection{Ethical Considerations}
Camera-based authentication can affect privacy even when it runs locally.
Users may not always expect a desktop application to process facial information continuously.
The system should therefore make camera state visible, ask for consent before enrollment, and provide a clear way to stop the session.
It should also avoid collecting more data than necessary.

The project should not be presented as a replacement for strong authentication.
It is better understood as an additional layer that can improve awareness and reduce unattended-session risk.
Final security decisions should still depend on the operating system, user permissions, and established authentication mechanisms.
This framing keeps the project realistic and avoids overstating what the prototype can guarantee.

\section{Conclusion}
This project shows that a local computer-vision workflow can support gesture recognition and continuous authentication concepts in a desktop application.
The system combines an Electron and React interface with a Python FastAPI AI service.
It records gesture samples, validates hand presence, trains a local gesture model, runs live inference, and triggers desktop actions only after a confident prediction.
The declared BSP scope also includes face recognition and user presence monitoring so that the system can verify whether an authorized user remains at the workstation.

VisionGuard is still a prototype, but it provides a complete foundation for future work.
The most important contribution is the end-to-end connection between user-facing camera workflows and local AI model operations.
This makes the system practical to test and extend.

\section{Future Work}
\subsection{Stronger Continuous Authentication}
The current prototype includes identity and model-family concepts, while the main completed workflow is gesture recognition.
The next implementation step is to complete face recognition, behavioral signals, and multimodal scoring to support the continuous-authentication target declared in the BSP.

\subsection{Improved Gesture Model}
The gesture model can be improved with richer landmark features, temporal motion features, and better calibration.
A stronger model should compare not only one frame but also short sequences so that dynamic gestures such as swipes can be recognized more accurately.

\subsection{Cross-Platform Action Support}
Desktop action execution is currently demonstrated on macOS.
Future work must add Windows and Linux support through platform-specific adapters.
This is required to satisfy the declared multi-platform target of Windows, Linux, and macOS.

\subsection{Dataset and Model Persistence}
The current AI service stores training state in memory while model artifacts are written locally.
A future version can persist datasets, jobs, metrics, and model metadata in a structured database.
This would make the system more reliable across restarts and easier to audit.

\subsection{Container and Deployment Improvements}
The Docker setup can be improved with a more complete development and deployment configuration.
A future version should define clear container profiles for development, testing, and demonstration.
It should also document how the desktop application connects to the local AI service when the service runs inside a container.
If several services are added later, Docker Compose can be used to start the AI service, storage layer, and supporting tools with one command.

\subsection{Evaluation}
The next step is to evaluate the system with repeated gesture and authentication trials.
Useful metrics include gesture recognition accuracy, false activation rate, authentication acceptance and rejection performance, task execution time, training time, inference latency, operating-system compatibility, reliability, and user-perceived usability.
This would make it possible to compare different models, thresholds, and platform adapters.
